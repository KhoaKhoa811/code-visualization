# Controlled runner prototype

This Java 21 harness checks isolated compilation, execution, bounded output, cancellation, and cleanup for seven reviewed fixtures. It is a bounded Milestone 1 feasibility slice; Milestone 0 specifications remain incomplete. It is not connected to Spring Boot or the frontend, and is not an arbitrary-source service.

Update 2026-09-21: the approved [controlled array recording experiment](recording/README.md) adds an optional trace channel and manual recorder fixtures. The output-only path remains available. The test script now includes recorder/stream tests and generated draft-1 result validation. No Spring Boot or frontend integration exists.

## Run on Windows

Requires host Java/javac 21, Node 22 for generated trace validation, PowerShell, a running Docker Desktop Linux engine, and this already-cached linux/amd64 image:

```text
docker.io/library/eclipse-temurin@sha256:87f0a5e638d0bc739f2908adb4a0a697b585d8bee5e5a8de43c88e8d07b3786e
```

From the repository root:

```powershell
& ./runner/prototype/test.ps1
```

The script compiles only the trusted harness and test driver on the host into `.build/`. Fixture `Main.java` files are transferred over Docker exec stdin and compiled/executed inside their own containers. There are no host mounts, silent image pulls, external Java dependencies, or host-execution fallback. Java program stdin is closed; Scanner interaction is a later increment.

## Implementation boundaries

- `RunnerHarness.java` owns lifecycle, stage deadlines, stdout/stderr byte collection, terminal cause, and cleanup. `Result` is an internal prototype record, not the draft trace/API contract. It includes source SHA-256 and the unique container identity.
- Docker compilation and execution are separate commands. `ExecEvidence.java` confirms each completed command using Docker management-channel `exec_create` and `exec_die` events, matched by container ID, exact command, and exec ID. The completion exit code must agree with the CLI exit code. Missing, invalid, or conflicting evidence reports an infrastructure error with no confirmed program exit code. Program output cannot supply this evidence, and exit codes 125/126/127 are not reserved as Docker errors. Nonzero confirmed program exit is a runtime failure, without claiming every failure is an exception or memory exhaustion. See [ADR 0003](../../specs/decisions/0003-runner-execution-evidence.md).
- Each container uses UID/GID 10001, no network, read-only root, dropped capabilities, no-new-privileges, default Docker seccomp, 512 MiB memory with no swap, one CPU, 128 tasks, and 56+8 MiB private tmpfs. Docker logging is disabled.
- Source is capped at 64 KiB. Compilation gets 15 seconds, execution 5 seconds, and overall orchestration 30 seconds; cleanup gets a separate 5-second observation budget. Program heap is 64 MiB and compiler heap 256 MiB, within the container cap.
- Daemon clock lookup and evidence queries each have a 3-second maximum and share the existing stage/overall deadlines. The event cutoff uses daemon `SystemTime` after exec; event timestamps must not exceed it. Management output has a separate 64 KiB bound. Failures include bounded aggregate diagnostics without raw management text. Docker retains only a limited event history; missing history or incompatible event fields produce an infrastructure error, even if the program actually finished. This conservative prototype approach needs reevaluation for a busy shared engine. See the [cutoff refinement](../../specs/docker-exec-evidence-fix.md).
- Compiler and program stdout/stderr share a 1 MiB retained-byte budget. Streams are drained concurrently, including output without newlines. Ordering is preserved within each stream, with no claimed cross-stream ordering. Overflow commits a terminal cause and leads to whole-container removal.
- First committed terminal cause wins; cleanup is reported separately. Admission is single-flight per harness instance. Unconfirmed cleanup blocks further use of that instance. This is not cross-process admission or durable orphan recovery.
- The fixed container PID 1 sleeps for 30 seconds, providing a lifetime backstop for these controlled fixtures. This does not prove tamper resistance or crash recovery for hostile submissions. Container metadata can remain after a driver crash; persistent ownership/recovery is unfinished.
- Cleanup removes only the UUID name generated by the current invocation, then checks that exact name is absent. If the engine cannot be contacted, absence is unconfirmed. A five-second observation bound cannot guarantee termination when Docker is unavailable.

## Acceptance cases

| Fixture | Expected evidence |
| --- | --- |
| success | Exact `ARRAY=1,1` stdout and `STDERR` stderr, both without newlines |
| compile-error | Compiler location, compile failure, no program launch |
| runtime-error | Nonzero execution and controlled exception diagnostic |
| timeout | Infinite loop reaches the 5-second program deadline |
| cancel | Cancellation after launch; `READY` proves main started before cancellation |
| output-limit | Combined stdout/stderr capture stops at 1 MiB and is marked truncated |
| heap-exhaustion | Allocation exceeds the fixed JVM heap; runtime failure and expected controlled diagnostic |

Every case checks container removal, bounded retained bytes, and overall elapsed time. The heap case does not prove Docker cgroup OOM enforcement. The diagnostic is evidence about this known fixture, not a spoof-proof classification rule for arbitrary code.
