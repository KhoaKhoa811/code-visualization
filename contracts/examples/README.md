# Draft Run-Result Fixtures

## Draft-3 loop fixtures added 2026-09-29

The six new fixtures are designed examples for [the first classic for loop](../../specs/for-loop-array-recording.md). They were assembled from the specified expected event sequence, not generated by executing or analyzing Java. The `.java` files below are source snapshots whose logical filename is Main.java; no submitted Java was compiled or run for this contract task. Each sourceId is the SHA-256 of the exact UTF-8/LF snapshot, unlike the illustrative IDs in the older fixtures below.

| Result | Source snapshot | Expected coverage |
| --- | --- | --- |
| [loop-success.json](loop-success.json) | [loop-success.java](sources/loop-success.java) | 13 steps, three stores, final false condition retires i |
| [loop-prefix.json](loop-prefix.json) | [loop-prefix.java](sources/loop-prefix.java) | Same facts with original ++i highlights |
| [loop-zero.json](loop-zero.json) | [loop-zero.java](sources/loop-zero.java) | Empty array, four steps, first condition false |
| [loop-limit.json](loop-limit.json) | [loop-success.java](sources/loop-success.java) | Twelve safe steps; i=3 remains because the final condition was not recorded |
| [loop-runtime-error.json](loop-runtime-error.json) | [loop-runtime-error.java](sources/loop-runtime-error.java) | Initial i=-1; four safe steps ending with true; no successful store/update/exit |
| [loop-output-only.json](loop-output-only.json) | [loop-success.java](sources/loop-success.java) | Illustrative unavailable visualization with null events/boundary |

Failure text is illustrative, not a captured exception message. The output-only example models the existing unavailable-result envelope, not an implemented loop execution path. No fixture claims runtime-loop support.

The validator self-test checks the six fixtures, all 1–12-step partial prefixes, rejection mutations, source hashes/exact highlights and independently expected cursor states in both directions. At the success fixture's final step, i is absent; stepping back restores i=3. This is a test-only reconstruction of known fixture data. Byte truncation of JSON is rejected rather than treated as a successful atomic scope exit; streaming transport behavior still needs the future collector tests.

## Temporary conventions

Update 2026-09-19: the [draft schema and validator](../README.md) now enforce these conventions for the four fixtures. They remain a narrow draft, not a finalized production protocol. Run `node contracts/validate.mjs --self-test` from the repository root. Zero-operation recordings and general step/bookkeeping mappings remain outside this draft.

- Fields and enum spellings remain proposals. Each result uses draft-1, one-based UTF-16 source columns, exclusive range ends, and one event per observable step for these examples only.
- Each sourceId refers exactly to its source block below (Main.java, LF separators). IDs are illustrative, not computed hashes. Object and variable IDs are scoped to their run.
- safePlaybackBoundary is present on playable examples and null when unavailable. events is null for unavailable visualization; a valid recording with zero operations would use an array, not null. Empty-recording boundary semantics remain unresolved. These null conventions are fixture proposals, not finalized schema decisions.
- The console field is a proposed terminal stdout/stderr summary, separate from trace events. It does not define live WebSocket messages. An empty stderr in a synthetic fixture does not promise that a real JVM emits no stack trace; console capture fidelity remains runtime verification work.
- Runtime-error coverage is partial here because only the declaration state is modeled; the diagnostic is not an exception event or an extra Step. Whether a fully captured exception can count as complete coverage remains unresolved.
- Frame/scope startup and teardown remain omitted, as in the trace draft. Complete means complete coverage of this illustrative observable sequence, not proof of a production lifecycle schema. Final-state visibility remains open.
- No automatic rerun, partial instrumentation strategy, or continuation after recorder failure is authorized by these examples.

## Expected behavior

| Fixture | Execution / visualization | Safe states in order |
| --- | --- | --- |
| [array-success.json](array-success.json) | completed / complete | [3, 1], [3, 1], [1, 1] |
| [runtime-error.json](runtime-error.json) | failed / partial | [3, 1]; display failure at values[5], without a successful read or initialized x |
| [output-only.json](output-only.json) | completed / unavailable | No diagram playback; show stdout and limitation |
| [partial-visualization.json](partial-visualization.json) | limited / partial | [3, 1], [7, 1]; never claim this is the program's final state |

Backward reconstruction must recover earlier states from the same recording without Java execution or stdin replay. Diagnostic locations do not advance the playback cursor.

The output-only case deliberately assumes the current tracer cannot handle Math.abs(int); it does not declare that method invalid or permanently unsupported. Execution admission and isolation are assumed satisfied for the scenario and still require implementation/testing. Its stdout is an expected value, not captured evidence.

The partial fixture assumes collection preserves two records before a recording limit leads to termination. The exact interruption point after the prefix is unknown: no successful values[1] write is asserted or reconstructed. Concrete limit values and termination races remain specification work.
